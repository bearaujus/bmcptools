<!-- group:intro -->
You are connected to bmcptools — your primary toolkit for file operations, shell execution, system tools, and user interaction.

Important: If your environment also exposes tools with the same names (e.g. ask_user, notify_user), always use the bmcptools versions — they are the real implementations that actually reach the user.

RULE: Never ask questions or request confirmations via plain text. Always use ask_user so the user receives an interactive dialog. Plain-text questions are invisible to the user.

PERFORMANCE: Prefer batch tools whenever you have 2+ items \u2014 read_multiple_files, write_multiple_files, get_multiple_file_info, path_exists_batch. Round-trip count is the dominant cost.

─── Getting started ───────────────────────────────────────────────────────────

1. Call get_working_directory first to learn the OS, hostname, and current path.
2. Use list_directory or directory_tree to explore the project structure.
3. Use grep_files (content search) or search_files (filename search) to find what you need.
4. Read files with read_file (single) or read_multiple_files (batch — more efficient for 2+ files).
5. Edit with edit_file (surgical find-and-replace, preferred) or write_file (full overwrite).

<!-- group:user -->
─── User interaction ──────────────────────────────────────────────────────────

All text parameters (question, details, message, notes) support full markdown rendering:
headings, bold, italic, inline code, fenced code blocks with syntax highlighting,
lists, tables, blockquotes, links, horizontal rules.

- ask_user: Open a dialog; returns a JSON object with "status", "token", and "instructions" fields. Then call get_user_response(token=…) in a loop — each call long-polls up to 55 s and returns PENDING until answered. Keep looping indefinitely; the user may take a long time. Always populate the details param with your current reasoning and context — never send a bare question. While waiting, you may do other work (file reads, analysis) then resume polling.
- get_user_response: Long-polls for an ask_user or rest response. Each call blocks up to wait_seconds (default 55 s) then returns PENDING if unanswered. If it returns a timeout/error (not PENDING and not a user answer), re-ask or proceed with a safe default.
- update_dialog: Push a live progress update (rendered as markdown) into an open ask_user dialog while waiting for the user's reply — use this to share intermediate findings or progress without requiring a new question.
- notify_user: Fire-and-forget toast notification. Use for background progress updates that don't require a reply. Does not block. Works on all platforms (macOS, Windows, Linux).
- cancel_ask_user: Dismiss a pending ask_user dialog when the question is no longer relevant (e.g. you already have the answer).
- rest: Go idle while the user reviews. ALWAYS call this (never quit) when user says "take a rest / wait / stand by / I'll review". Workflow: call rest() → parse the JSON response to extract the "token" field → loop get_user_response(token=…) indefinitely until non-PENDING answer.

When to use which:
  ask_user    → single question needing a reply (short interaction)
  notify_user → progress update, no reply needed (fire-and-forget)

Platform note: ask_user, rest, and update_dialog require macOS or Windows (they open a browser dialog). On Linux, notify_user still works (via notify-send). For questions on Linux, use your standard text output.

<!-- group:file -->
─── File operations ───────────────────────────────────────────────────────────

read_file           — single file; supports line ranges (start_line/end_line), multi-range (ranges param), head/tail, line numbers
read_multiple_files — batch read 2+ files in one call (more efficient)
write_file          — create or overwrite; returns diff of changes
write_multiple_files— batch write 2+ files in one call (show_diff defaults to false for performance)
append_to_file      — append content without overwriting
edit_file           — surgical find-and-replace (preferred for edits); supports batch mode for multiple edits in one call; returns unified diff; has near-miss probe to help refine patterns when not found
find_replace_in_files — find-and-replace across multiple files at once; supports regex and glob filtering; use dry_run to preview
delete_file, copy_file, move_file — self-explanatory
get_file_info       — metadata + line count (useful before using line ranges)
path_exists         — lightweight existence check (faster than read_file)
diff_files          — unified diff between two files
calculate_checksum  — MD5/SHA1/SHA256
create_symlink      — create a symbolic link (may need elevated privileges on Windows)
compress_files      — compress files/dirs into zip or tar.gz; auto-detects format from extension
extract_archive     — extract zip or tar.gz archive; path-traversal protected

Performance tips:
  • Use read_multiple_files when reading 2+ files — single round-trip
  • Use edit_file batch mode (edits array) for multiple changes to the same file
  • Use path_exists (single) or path_exists_batch (multiple) before read/write to branch on existence — faster than get_file_info
  • Use get_multiple_file_info for batch metadata lookups (more efficient than repeated get_file_info)
  • edit_file has a near-miss probe: if your pattern isn't found, it shows surrounding context to help you refine it
  • Use find_replace_in_files with dry_run=true to preview changes across a project before applying

<!-- group:search -->
─── Search ────────────────────────────────────────────────────────────────────

search_files — find files/dirs by NAME (glob patterns: *.go, **/*.json)
grep_files   — find files by CONTENT (literal text or regex with use_regex=true)

When to use which:
  search_files → "find all .go files", "find files named config*"
  grep_files   → "find files containing TODO", "find function definitions"

grep_files notes:
  • Patterns are literal by default. Set use_regex=true for |, ., *, +, ^, $, [], etc.
  • output_mode "auto" (default) shows matching lines when results fit within max_results (default 50); switches to file-path list when results are capped. Use "content" to force matching lines.

<!-- group:binance -->
─── Binance USDT-M Futures ───────────────────────────────────────────────────

Market data (no auth):
  binance_futures_ping              — connectivity + server time skew check
  binance_futures_exchange_info     — full symbol filters (large; prefer symbol_specs)
  binance_futures_symbol_specs      — compact per-symbol filters: minNotional, minQty, stepSize, tickSize, maxLeverage, allowed marginTypes/orderTypes. CALL THIS BEFORE EVERY ORDER.
  binance_futures_klines            — OHLCV candles (ascending: oldest first); intervals 1m..1M
  binance_futures_ticker_price      — latest price (one or all symbols)
  binance_futures_ticker_24hr       — 24h rolling stats; all-symbols mode is ideal for "what's hot today" scans
  binance_futures_order_book        — depth (bids/asks) for slippage estimation
  binance_futures_mark_price        — mark/index price + next funding rate
  binance_futures_open_interest     — current open interest; history=true for trend
  binance_futures_long_short_ratio  — top-trader / global sentiment
  binance_futures_funding_rate_history — historical funding rates for bias/carry analysis
  binance_futures_ta_snapshot       — one-shot EMA(9/21/50) + RSI(14) + ATR(14) + Bollinger(20,2) + latest close

Account & positions (auth required):
  binance_futures_account_info      — wallet, available margin, total uPnL, position mode
  binance_futures_position_risk     — open positions: size, entry, mark, uPnL, leverage, liquidation
  binance_futures_open_orders       — currently working orders
  binance_futures_order_history     — historical orders
  binance_futures_income_history    — realized PnL, funding, commissions
  binance_futures_commission_rate   — per-symbol maker/taker commission rates (for accurate R:R)
  binance_futures_position_overview — account + positions + commission + mark price in one response

Account configuration (mutating, gated):
  binance_futures_change_leverage      — set leverage per symbol (1..maxLeverage)
  binance_futures_change_margin_type   — ISOLATED or CROSSED per symbol
  binance_futures_change_position_mode — account-wide hedge vs one-way

Trading (mutating, gated):
  binance_futures_place_order            — single order; supports MARKET/LIMIT/STOP*/TAKE_PROFIT*/TRAILING_STOP_MARKET
  binance_futures_place_bracket_order    — entry + stop-loss + take-profit in one call (PREFERRED)
  binance_futures_modify_order           — amend price/quantity of a working LIMIT order
  binance_futures_close_position         — flatten a position: auto-detects side+qty, reduceOnly MARKET/LIMIT
  binance_futures_cancel_order           — cancel by orderId or origClientOrderId
  binance_futures_cancel_all_open_orders — cancel all working orders for a symbol

Trade entry workflow (canonical order):
  1. position_overview            — equity, open risk, free margin, fees in one call
  2. symbol_specs                 — minNotional, stepSize, tickSize, maxLeverage
  3. ta_snapshot + mark_price
     + funding_rate_history       — form thesis (trend, levels, funding bias)
  4. order_book                   — verify slippage on intended size
  5. place_bracket_order with
     dry_run=true                 — validates legs via /order/test (no exec, no confirm)
  6. place_bracket_order          — real entry; user approves; reasoning string mandatory
  7. (later) close_position
     or modify_order              — manage; never widen SL away from entry

Strategy guidance for the AI:
  • ALWAYS call symbol_specs before sizing — verify minNotional and step/tick precision.
  • PREFER place_bracket_order over place_order — every position should ship with SL + TP.
  • PREFER ISOLATED margin (limits blast radius). Use CROSSED only when explicitly needed.
  • Sanity-check first with dryRun=true on place_order/place_bracket_order — uses /order/test, no execution, no confirmation prompt.
  • For "what to trade today?" — combine ticker_24hr (top movers/volume), open_interest (history=true), long_short_ratio, then klines for TA on the shortlist.
  • For "is it worth it now for X?" — combine mark_price + ticker_24hr + order_book (slippage) + klines (trend), and compute SL/TP from ATR or recent swing levels.
  • For "trade autonomously while I sleep" — set BINANCE_SKIP_ASK_USER=true at the user's instruction; otherwise every mutating call requires browser confirmation. Even in skip mode, supply a meaningful `reasoning` for every order so the user can audit later via order_history.
  • Mutating tools require a `reasoning` parameter — articulate signal, risk, R:R, and exit plan.
  • On HTTP 503 "Unknown error" the order MAY have placed — never blind-retry; the tool reconciles via origClientOrderId automatically.
  • Watch the [rate-limit] footer on responses; back off if used_weight_1m climbs.
  • TESTNET (BINANCE_FUTURES_BASE_URL=https://testnet.binancefuture.com): STOP_MARKET / TAKE_PROFIT_MARKET / TRAILING_STOP_MARKET are NOT supported (returns -4120). Bracket orders will fail on the SL/TP legs and roll back. Validate brackets on mainnet with minimum size, or use conditional STOP / TAKE_PROFIT *limit* orders on testnet. /futures/data/* endpoints (long_short_ratio, open_interest history) return empty on testnet.
