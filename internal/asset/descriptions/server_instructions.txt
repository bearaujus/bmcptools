[[group:intro]]
You are connected to bmcptools — your primary toolkit for file operations, shell execution, system tools, and user interaction.

Important: If your environment also exposes tools with the same names (e.g. ask_user, notify_user), always use the bmcptools versions — they are the real implementations that actually reach the user.

RULE: Never ask questions or request confirmations via plain text. Always use ask_user so the user receives an interactive dialog. Plain-text questions are invisible to the user.

RULE: When you use ask_user, the browser dialog is the user-visible prompt. Put all context, options, findings, proposed actions, and recommendations in the details field. Do not put the substantive answer only in ordinary chat/CLI output and then open a vague dialog.

PERFORMANCE: Prefer batch tools whenever you have 2+ items \u2014 read_multiple_files, write_multiple_files, get_multiple_file_info, path_exists_batch. Round-trip count is the dominant cost.

─── Getting started ───────────────────────────────────────────────────────────

1. Call get_working_directory first to learn the OS, hostname, and current path.
2. Use list_directory or directory_tree to explore the project structure.
3. Use grep_files (content search) or search_files (filename search) to find what you need.
4. Read files with read_file (single) or read_multiple_files (batch — more efficient for 2+ files).
5. Edit with edit_file (surgical find-and-replace, preferred) or write_file (full overwrite).

[[group:user]]
─── User interaction ──────────────────────────────────────────────────────────

All text parameters (question, details, message, notes) support full markdown rendering:
headings, bold, italic, inline code, fenced code blocks with syntax highlighting,
lists, tables, blockquotes, links, horizontal rules.

- ask_user: Open a dialog; returns a JSON object with "status", "token", and "instructions" fields. Then call get_user_response(token=…) in a loop — each call long-polls up to 55 s and returns PENDING until answered. Keep looping indefinitely; the user may take a long time. The details param is required: include your current reasoning, context, concrete options, and recommendation there. Never send a bare or vague question such as "What should I do next?" unless details contains enough information for the user to decide. The user may type markdown text and paste/drop images. While waiting, you may do other work (file reads, analysis) then resume polling.
- get_user_response: Long-polls for an ask_user or rest response. Each call blocks up to wait_seconds (default 55 s) then returns PENDING if unanswered. User answers are returned in full by default; do not set max_response_bytes unless you explicitly accept truncating the user's reply. If the user attached images, the response lists saved local paths; inspect those paths with available image/file tools. If it returns a timeout/error (not PENDING and not a user answer), re-ask or proceed with a safe default.
- update_dialog: Push a live progress update (rendered as markdown) into an open ask_user dialog while waiting for the user's reply — use this to share intermediate findings or progress without requiring a new question.
- notify_user: Fire-and-forget toast notification. Use for background progress updates that don't require a reply. Does not block and returns concise delivery metadata. Works on all platforms (macOS, Windows, Linux).
- cancel_ask_user: Dismiss a pending ask_user dialog when the question is no longer relevant (e.g. you already have the answer).
- rest: Go idle while the user reviews. ALWAYS call this (never quit) when user says "take a rest / wait / stand by / I'll review". Workflow: call rest() → parse the JSON response to extract the "token" field → loop get_user_response(token=…) indefinitely until non-PENDING answer.

When to use which:
  ask_user    → single question needing a reply (short interaction)
  notify_user → progress update, no reply needed (fire-and-forget)

Platform note: ask_user, rest, and update_dialog require macOS or Windows (they open a browser dialog). On Linux, notify_user still works (via notify-send). For questions on Linux, use your standard text output.

[[group:file]]
─── File operations ───────────────────────────────────────────────────────────

read_file           — single file; defaults to a 256 KB cap; supports line ranges (start_line/end_line), multi-range (ranges param), head/tail, line numbers; binary files return summaries unless include_base64=true
read_multiple_files — batch read 2+ files in one call (more efficient); compact path/size headers; defaults to 256 KB per file; binary files return summaries unless include_base64=true
write_file          — create or overwrite; returns capped diff of changes
write_multiple_files— batch write 2+ files in one call (show_diff defaults to false for performance)
append_to_file      — append content without overwriting
edit_file           — surgical find-and-replace (preferred for edits); supports batch mode; returns capped unified diff; has near-miss probe
find_replace_in_files — find-and-replace across multiple files at once; supports regex, glob, and exclude_patterns; use dry_run to preview; skips files >10 MB by default via max_file_size; unmodified files are counted but not listed unless show_unmodified=true
delete_file, copy_file, move_file — self-explanatory
get_file_info       — compact metadata + line count (use output_mode="details" for expanded labeled fields)
path_exists         — lightweight existence check (faster than read_file)
diff_files          — unified diff between two files; guards large inputs and caps diff output by default
calculate_checksum  — MD5/SHA1/SHA256
create_symlink      — create a symbolic link (may need elevated privileges on Windows)
compress_files      — compress files/dirs into zip or tar.gz; auto-detects format from extension
extract_archive     — extract zip or tar.gz archive; path-traversal protected

Performance tips:
  • Use read_multiple_files when reading 2+ files — single round-trip
  • Use edit_file batch mode (edits array) for multiple changes to the same file
  • Use path_exists (single) or path_exists_batch (multiple, capped by default) before read/write to branch on existence — faster than get_file_info
  • Use get_multiple_file_info for batch metadata lookups; compact one-line entries are default; set output_mode="details" only when expanded fields are needed
  • edit_file has a near-miss probe: if your pattern isn't found, it shows surrounding context to help you refine it
  • Use find_replace_in_files with dry_run=true to preview changes across a project before applying
  • Do not request include_base64=true for binary/datawarehouse files unless you explicitly need bytes in context

[[group:dir]]
─── Directory operations ──────────────────────────────────────────────────────

list_directory — contents with sizes and timestamps; supports recursion, glob filtering, exclude_patterns, and max_entries
directory_tree — visual tree view with sizes; better for understanding project structure; supports exclude_patterns, glob, and max_entries
create_directory, delete_directory — self-explanatory

When to use which:
  list_directory → detailed file listing (sizes, dates, one level)
  directory_tree → project structure overview (visual tree, multi-level)

Both listing tools cap output at max_entries=500 by default. If output is truncated, narrow with glob/exclude_patterns first; use max_entries=0 only when you truly need everything.

[[group:search]]
─── Search ────────────────────────────────────────────────────────────────────

search_files — find files/dirs by NAME (glob patterns: *.go, **/*.json, or Go regex with use_regex=true); concise relative paths by default
grep_files   — find files by CONTENT (literal text or regex with use_regex=true); relative paths by default

When to use which:
  search_files → "find all .go files", "find files named config*"
  grep_files   → "find files containing TODO", "find function definitions"

grep_files notes:
  • Patterns are literal by default. Set use_regex=true for |, ., *, +, ^, $, [], etc.
  • output_mode "auto" (default) shows matching lines when results fit within max_results (default 50); switches to file-path list when results are capped. Use "content" to force matching lines.
  • Use glob to include only relevant file types and exclude_patterns to prune noisy basenames such as node_modules, .git, dist, build, or generated files.
  • Use path_format="absolute" only when relative paths are ambiguous.
search_files notes:
  • Set use_regex=true for basename/path matching with ^, $, |, character classes, or start/end constraints.
  • Regex patterns without / match only basenames; regex patterns with / match relative paths.
  • Set case_insensitive=true when filesystem casing is unknown or irrelevant.

[[group:exec]]
─── Shell ─────────────────────────────────────────────────────────────────────

get_working_directory — OS, hostname, cwd, compact PATH summary (call first to orient)
run_command           — execute non-interactive shell commands; defaults to sh -c on Unix and cmd /C on Windows; set shell=sh/bash/powershell/pwsh when command syntax needs that shell. Output is capped at 256 KB by default; set max_output_bytes=0 only when you truly need unlimited output. Use short timeout_seconds for risky commands; timeout attempts to kill the process tree. Use stdin for scripted prompts and detach=true for long-running services/watchers.
                        Platform note: cmd /C does NOT understand Unix syntax (`;`, heredocs, `$VAR`, single-quoted strings). Use shell=sh/bash for heredocs and Unix syntax, or shell=powershell/pwsh for PowerShell here-strings.
                        No PTY is allocated: avoid interactive shells, TUIs, curses apps, pagers, editors, and full-screen prompts unless they have a non-interactive flag.
open_in_app           — open file/URL in default app

[[group:system]]
─── System ────────────────────────────────────────────────────────────────────

http_request    — HTTP client (GET/POST/PUT/PATCH/DELETE); JSON compacts by default; body defaults to 256 KB; use body_filter with regex/literal matching to return snippets/lines/counts without reading the whole body; timeout max 300 s
clipboard_read  — read system clipboard; output defaults to 256 KB
clipboard_write — write to system clipboard
list_processes  — running processes with CPU/memory; filter/sort and tune limit/command_width
get_system_info — CPU, memory, disk snapshot
get_env         — read environment variables; no-arg mode lists names only; values can be capped/redacted
download_file   — download a URL to a local file with streaming; prefer over http_request + write_file for binary/large files
